A **pipeline** writes several commands before it waits for any reply, then returns one `Result` per command in the same order. Each command keeps its own success type, and one failure does not hide the others.

**Example** (Pipelining a Write and a Counter)

```ts twoslash
import { Effect, Result } from "effect";

import { Commands, Redis } from "@effect-kit/redis";

const program = Effect.gen(function* () {
  const redis = yield* Redis;

  const results = yield* redis.pipeline([
    Commands.set("{account:42}:name", "Ada"),
    Commands.incr("{account:42}:visits"),
  ]);

  const [saved, visits] = results;
  //     ^?

  if (Result.isFailure(visits)) return yield* visits.failure;

  return visits.success;
});
```

`redis.pipeline` takes `Commands.*` values. The result is a tuple, so `saved` is typed for `set` and `visits` for `incr`. The Effect fails only when the batch as a whole fails. A command the server rejects comes back as a `Failure` inside the tuple.

<Callout type="warn" title="Pipelines are not atomic">
  A pipeline is not a transaction. Other clients can run commands between yours, and commands that
  succeed stay applied when a later one fails. Use a [transaction](/docs/redis/transactions) when
  the commands must run together.
</Callout>

## Getting plain values with batch

`redis.batch` runs the same kind of command tuple in order, but succeeds with the plain values instead of `Result` wrappers. Use it when any failed command should fail the whole step. Use `pipeline` when you want to handle each failure yourself.

**Example** (Reading Values From a Batch)

```ts twoslash
import { Effect } from "effect";

import { Commands, Redis } from "@effect-kit/redis";

const program = Effect.gen(function* () {
  const redis = yield* Redis;

  const values = yield* redis.batch([Commands.get("greeting"), Commands.incr("visits")]);
  //    ^?

  return values;
});
```

`redis.batch([])` succeeds with `[]`, and a batch holds at most `256` commands. Like a pipeline, a batch is ordered and not atomic.

If any command fails, the whole batch fails with a `BatchError` whose `phase` is `"pipeline"` and whose `execution` is `"replied"`. The batch reads every reply first, so the `outcomes` list, which is `Redacted`, covers every command by index.

On Node and Bun, a batch shares the ordinary connection. Upstash HTTP, cluster and sentinel clients use their own batch paths and keep their routing rules, such as the [hash tag rule](/docs/redis/cluster/multi-key) on a cluster.

## Reusing a compiled plan

`redis.compile` takes commands whose arguments are fixed and returns a `CompiledBatch`. Calling `execute()` on it returns the same values tuple as `batch`. Compile once when you run the same commands many times.

**Example** (Compiling and Executing a Plan)

```ts twoslash
import { Effect } from "effect";

import { Commands, Redis } from "@effect-kit/redis";

const program = Effect.gen(function* () {
  const redis = yield* Redis;

  const plan = yield* redis.compile([Commands.get("greeting"), Commands.get("visits")]);

  const first = yield* plan.execute();
  //    ^?
  const second = yield* plan.execute();

  return [first, second];
});
```

Compiling copies the arguments, including bytes, so changing a buffer afterwards does not change the plan. The native encoding is reused after the first run. Schema key encoders are required when you compile, and decoder services are required when you execute.

A plan accepts up to `256` commands and `16 MiB` of encoded input. Provider and connection limits are checked again on every execution.

<Callout type="warn" title="A plan belongs to its client">
  Execute a plan only while the client that compiled it is open. After the client scope closes,
  `execute()` fails with a `ConnectionError` whose `reason` is `"closed"`.
</Callout>

If a fiber is interrupted after a command may have been written, the shared Node or Bun connection is retired. Other requests waiting on that connection are affected too.

## Checking each result

A failing command does not fail the pipeline, so the Effect succeeds even when a result is a `Failure`. Ignoring the results hides the error.

**Example** (Reading a Failure From a Pipeline)

```ts twoslash
import { Effect, Result } from "effect";

import { Commands, Redis } from "@effect-kit/redis";

const program = Effect.gen(function* () {
  const redis = yield* Redis;

  const [saved, counted] = yield* redis.pipeline([
    Commands.set("profile:name", "Ada"),
    Commands.incr("profile:name"),
  ]);

  // Wrong: the pipeline succeeded, but INCR failed on a text value.
  // return "ok";

  // Right: look at each result. SET is still applied.
  if (Result.isFailure(counted)) {
    return `set ok: ${Result.isSuccess(saved)}, incr failed: ${counted.failure._tag}`;
  }

  return "both ran";
});
// Output: set ok: true, incr failed: ServerError
```

Each failure is a `ServerError` or a `ReplyError`, or an error from a custom decoder.

## When the whole batch fails

If the connection fails or the fiber is interrupted partway through, the pipeline fails with a `BatchError`. Its `outcomes` field is `Redacted` because replies can hold your data. It records what happened to each command by index: `Completed`, `Replied`, `Unsent` or `Unknown`.

**Example** (Inspecting Per-Command Outcomes)

```ts twoslash
import { Effect, Redacted } from "effect";

import { Commands, Redis } from "@effect-kit/redis";

const program = Effect.gen(function* () {
  const redis = yield* Redis;

  return yield* redis
    .pipeline([Commands.incr("jobs:done"), Commands.incr("jobs:total")])
    .pipe(
      Effect.catchTag("BatchError", (error) =>
        Effect.succeed(Redacted.value(error.outcomes).map((slot) => slot._tag)),
      ),
    );
});
```

A slot marked `Unsent` never reached the server. A slot marked `Unknown` may have run. `execution` on the error summarizes the batch: `partial-or-unknown`, `not-executed`, `unknown` or `replied`.

## Batch limits

A pipeline holds at most `maxBatchCommands` commands, which defaults to `256`. A longer one fails before anything is written, with a `SessionError` whose `reason` is `"batch-limit"`. An empty pipeline returns `[]`.

Set the limit in the layer's `sessions` options.

**Example** (Raising the Batch Limit)

```ts twoslash
import { RedisNode } from "@effect-kit/redis/node";

export const RedisLive = RedisNode.layer({
  url: "redis://localhost:6379",
  sessions: { maxBatchCommands: 1000 },
});
```

On a cluster, give the keys in one pipeline the same hash tag, as the `{account:42}` keys above do. See [multi-key commands](/docs/redis/cluster/multi-key).
